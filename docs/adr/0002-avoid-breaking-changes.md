# Avoid breaking changes: deprecate for one minor release

Projects built on Roadiz must be able to upgrade without rewriting their code at every minor release. Breaking changes are therefore avoided as much as possible, in every package of this repository: a change that would break an **extension point** ships with a deprecated compatibility layer for one minor release instead. An extension point is a mechanism documented on a page of `docs/` written for projects (bundle configuration, dependency injection tags, events, the classes, interfaces and services the docs cite, API resources, Twig blocks of the backoffice entry points, Twig components and their options, the design tokens of `theme.css`); contributor pages (`docs/developer/contributing/`, `docs/adr/`, `docs/agents/`) and comments in the code do not make a mechanism public, and anything undocumented is internal and may change in any release. A **breaking change** is a change that makes a project working on a tagged release fail, or behave differently from what the docs describe, without touching its code, through an extension point present in that release. Anything added since the last tag is not released yet and may change freely.

We rejected keeping deprecations until the next major release (Roadiz ships breaking changes in minors, and a 2.x layer kept until v3 would pile up for years), case-by-case deprecation "when it costs little" (it left every break to review, and in practice to the break) and protecting every reachable template or class (any markup or refactor would break a project, so the codebase could no longer evolve).

## Consequences

- An extension point never changes in a patch release. When it changes in a minor release 2.N, the old form keeps working, deprecated, and is removed in 2.N+1.
- Only two cases may break an extension point without deprecation: a security fix whose old behaviour would keep the hole open, and a major upgrade of a dependency that forces the break with no reasonable compatibility layer. The PR justifies it and `UPGRADE.md` lists it.
- Calling an extension point is protected (`extends`, `include`, `embed` and `import` of a Twig template, PHP calls, configuration). Overriding a template other than an entry point is not: it was never a public mechanism (Rozier [ADR 0006](../../lib/Rozier/docs/adr/0006-projects-customise-through-public-mechanisms.md)).
- One way to signal a deprecation across the repository. PHP: `trigger_deprecation('roadiz/<package>', '<version>', …)` and an `@deprecated` tag. Twig: a stub left at the old path, with `{% deprecated %}` followed by `{% extends %}` or `{% include %}` of the new one. Every message gives the version that deprecates, the replacement and the version that removes. `UPGRADE.md` lists deprecations in a "Deprecated" section of each version, and an issue on the next minor's milestone gathers the removals.
- The rule applies to unmerged and future work. Breaking changes already merged for the unreleased 2.8 are audited separately against it ([#559](https://github.com/roadiz/core-bundle-dev-app/issues/559)), including mechanisms documented in 2.7 such as the UIkit icon classes of `roadiz_rozier.entries` and `<rz-entity-thumbnail>`.
- Transition for 2.8, a courtesy outside the definition: no template path but the entry points was documented in 2.7, yet the docs told projects to copy Rozier templates, and the `NSArticle` example they referred to includes `admin/base.html.twig`, `includes/column_ordering.html.twig`, `widgets/countFiltersBar.html.twig`, `admin/bulk_actions.html.twig` and `widgets/filtersBar.html.twig`. If 2.8 moves or removes them (Rozier [ADR 0005](../../lib/Rozier/docs/adr/0005-twig-components-move-in-v2-8.md)), these five keep a deprecated stub at their old path until 2.9. The other released templates are internal: `UPGRADE.md` lists those 2.8 moves or removes as removed, without a stub.
